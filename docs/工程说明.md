### V0.4.0 打包收藏改出 HTML
「多消息打包收藏」不再只是一堆 CSV 行：**一包一目录 + `index.html`**。

- 判定不看类型名，看 `<datalist count>`：**count ≥ 2 就是打包**（常见都是 type=14；
  count 达到 100 时即微信合并转发上限）。单图/单视频/单语音仍然是单文件。
- 目录：`<发送人>/聊天记录/<序号>_<收藏日期>/index.html`，附件与页面同目录，
  **页面全用相对路径**，整个目录可以直接拷走或打包发人。
- **不做总索引**（按需求）：入口就是 `_导出清单.csv`，父行的「输出路径」指向该包的 `index.html`、
  状态列写 `已生成HTML` / `HTML生成失败`。
- 语音/视频/位置尽量补齐：语音画时长条（无本体时写「本体不在本机」）、
  视频有本体就嵌播放器、只有封面就出封面帧并标注、位置给地址 + 高德地图链接；
  图片完整件可点开原图，缩略件带「本地仅缩略图」标记。
- 标题兜底：多数条目库里**没有**可用的 `<title>`，微信是渲染时拼的，这里按同一规则补
  `"<显示名>"的聊天记录`。
- 状态可见到「包」这一级：状态行写清成功/失败包数（例如 `聊天记录包 3/3`，失败时 `2/3（失败 1）`）、
  失败清单直接列出包名与原因、`_导出说明.txt` 有失败包清单、
  结果 JSON 有 `chat.packs_ok / packs_failed / failed_packs`。
- 单个包 HTML 失败**不拖垮整批**：其余包照常生成，失败的那个在五处状态里都能看到。

### V0.4.3 语音进清单 + 清单复核

**语音（type=3/8）现在默认进导出范围**（`DEFAULT_KINDS` 加 `voice`，注册表 `default_media` 同步）：

- 微信 PC 端**通常没有 silk 本体**（账号目录里往往搜不到 silk/amr/slk，`msg/attach/**/Voice` 也常是空的），
  所以这类语音只能登记成 **`仅元数据`**，不进「未取到原件」清单。
- 但**被当文件发过的语音**能救：可按 md5 在 `msg/file/*.mp3`、`msg/attach/**/F/*.mp3` 认领，
  认到就会导出并在页面里可播。
- `_导出报告.csv` 与 `_导出清单.csv` 口径统一：都写 `仅元数据`；时长从毫秒换成秒
  （type=3 的 `<duration>` 是毫秒）；清单摘要写「语音 · N 秒」。

**HTML 语音条按微信的样子重做**：胶囊 + 三根声波柱 + 时长，己方靠右、图标翻转；
有本体点一下就播（同时只播一条，播放时声波跳动），没本体点一下就地说明原因。

**新增 `tests/verify_manifest.py`：导出清单复核**。不看清单自己写的数字，而是从微信库与磁盘
反推 22 项，逐条对：序号连续唯一 / 父行数=打包数且指向存在的 index.html / 每包行数=子项数+父行 /
正文行数与原文逐条可比 / 媒体状态与文件一一对上 / 完整件 md5 == 库 fullmd5 / 路径不出批次 /
批次文件无孤儿 / 图片视频语音文本链接条数与库一致 / 报告与清单状态分布一致 / 语音行秒级时长 /
说明文件计数与实算一致。

多个抽样批次全过（每批全部核对项通过），其中包括含缩略/未定位的批次，以及补导前后各复核一次。

顺带修掉一个真 bug：`build_manifest_rows` 的排序键里 `parent` 一边是报告 CSV 的字符串、
一边是 chat_items 的 int，**同一条时间戳出现两次时**会抛 `TypeError`（补导后重写清单触发）。

### 未发版：补导对聊天记录附件空转（已修，计划 V0.4.3）

**现象**：到微信里重新加载图片后点「补导」，可能提示「升格 0 条」且仍显示未取到原件；
关掉软件重新导出，这些文件又能变成完整件。

**根因**：`retry_missing` 的待办过滤里有 `not 所属收藏`，而聊天记录里的附件，其报告行
`所属收藏` 一定非空 —— 于是这些行**全被过滤掉**，待办为空，函数走「没有需要补导的条目」
的提前返回分支，回 `upgraded=0, still_missing=0`。界面拿 `failed_count` 拼出「仍有 N 条」，
看起来像补导跑过但没升格，其实它根本没试。V0.3.0 加「所属收藏」列时就带进来了。

**修法**：
- 补导不再排除聊天记录附件，改为按**报告行自己的体积与 md5** 单条认领（包级别 query 给不出子项字段）。
- 升格后的文件写回**同一个包目录**（`<发送人>/聊天记录/<lid>_<日期>/`），去掉「_缩略」；
  已有不同内容的完整件仍不覆盖。
- 升格过的包**自动重渲 `index.html`**，否则文件换了、页面还写着「本机未缓存」。
- `_导出说明.txt` 里「聊天记录里的附件不参与补导」的旧说法一并改掉。

**验证**：`tests/verify_chatrecord.py` 新增 4 项（降级后确有附件待补导 / 补导能升格 /
完整件不再叫 _缩略 / 缩略数按升格数下降 / 页面已重渲），共 54 项全过。
用真实待补导批次复现：修复前 `upgraded 0, still_missing 0`，修复后附件能升格。

### V0.3.0 类型注册表 + 聊天记录展开 + 缓存还原

**一个类型只在一个地方定义**：新增 `src/type_registry.py`，把此前散在 `core/fav_export.py::kind_of`
与 `export_list.py` 两套互相矛盾的判断合并成一张表（`kind` / 中文名 / 是否有本体 / 是否文本 /
是否容器 / 是否在线内容 / 是否默认纳入）。`core/fav_export.py` 不再自带猜测逻辑，改为调用注册表；
未注册的类型显式降级为「未知类型 N」，不再悄悄并进 `其他`。

对着本地数据跑全量分类，**`kind=other` 降到 0**；未纳入普查收敛成语音和视频号 ——
剩下的都是有明确理由的（本体不在 PC / 在线内容）。

**type=14 聊天记录不再是空文件**：以前只写一个 0 字节 `.dat` 就标「完整」。现在解析 `datalist` 里的
`datatype` 属性，正文（文本、链接卡片等）逐条写入 `_导出清单.csv`，附件按 `<发送人>/聊天记录/` 落盘。
抽样复检中，正文写入清单、附件按完整/缩略落盘，子项四态（完整 / 缩略 / 未定位 / 仅元数据）互斥穷尽。

**`msg/attach/**.dat` 缓存还原**：这类缓存不是 V2 容器，而是**整文件单字节 XOR**（首字节
`0x78 ^ 0x87 = 0xFF` ⇒ `FF D8 FF E1` 的带 EXIF JPEG）。以前部分聊天图片被当成无法打开的 `.bin`
写出且标记「完整」。现在按已知 magic 反推异或键、解码后再验格式，解不出就退回「未定位」而不是写垃圾。
抽样还原后都能被 PIL 正常打开，未定位数量明显下降。

**批次清单与报告新增两列**：`_导出清单.csv` / `_导出报告.csv` 增加「所属收藏」（子项属于哪条收藏）
与「还原」（是否经缓存还原），聊天子项一行一条挂在父行下面。

**新增 `--install`**：静默安装 / 覆盖升级（`--install [--dir 目录]`），与安装向导走同一条
`installer.install()`，只是不弹窗，便于本机升级和以后做批量部署。

同一区间对比：聊天记录展开后落盘文件明显增多；
type=4 视频从「部分因缺少 `datafmt` 被错标进 `other`」变成全部正确归类。

### 环境初始化（V0.2.0 起，陌生电脑零手工配置）

未就绪时主按钮变为「初始化本机环境」，点开是一个三步窗口：

- **微信账号**：自动列出本机所有账号（含非默认存储路径），也可「浏览…」手动指定
- **数据库密钥**：点「提取密钥」从运行中的微信进程读取，普通权限即可；通常数秒内完成，绝大多数库可提取
- **图片密钥**：需先在微信里打开一张收藏图片，再点「开始检测」（约 30–60 s）；
  未捕获到可「手动填写」16 位密钥，写入前用本机容器校验命中数

三项就绪后按钮恢复「导出」。提取逻辑在 `src/core/wxkeys.py`，随 exe 一起分发，
不依赖外部脚本、不依赖本机 Python。命令行等价入口：`--cli --setup-keys`、`--cli --capture-image-key`。

### V0.1.0 默认导出与批次清单

主界面短路径仍是「文件夹、日期、导出」，不增加类型勾选。默认导出**图片、视频、文本（type=1）和链接卡片（type=5）**：
图片和视频写出文件后，在同一批次目录里按发送人再分子文件夹；完整件与缩略图放在同一人的文件夹里，缩略图用文件名「_缩略」区分。
文本全文和链接的标题、摘要、网址都写入 `_导出清单.csv`，**不另存单个 .txt / .md 文件**。
聊天记录打包（type=14）和文件、语音默认不纳入。**`kinds=link` 仍表示 type=14 打包聊天，不是公众号文章。**

若有未取到原件的图片或视频，主界面会给出处理提示，并可对同一批次点「补导」，不必重新选择日期和文件夹。

每个成功批次目录除按发送人分好的文件夹、`_导出报告.csv` 外，还会生成：

- `_导出清单.csv`：本批默认范围内的图片、视频、文本、链接，一行一条；文本含全文，链接含标题/摘要/网址，媒体含状态与输出路径
- `_未取到原件.csv`：未取到原件的媒体，含中文类型、状态、原因、建议（例如先在微信点开大图或真正播放视频再导出）和可读名称
- `_导出说明.txt`：给人看的说明（含当天的日期范围、本批实际类型、四态计数、按发送人分文件夹的目录含义、补导说明，以及同期未纳入的类型数量；数量为 0 的不单独强调）
- `_补导状态.json`：关掉程序后仍可对同一批次补导（不含密钥与账号路径）

`_导出报告.csv` 的列保持核心脚本原样，便于与基线对账。它只覆盖走文件导出的条目（默认是图片和视频）。

CLI / MCP 的 `kinds` 仍然只选择 `resolve_item` 类型：`image,video,file,link,chat`。
**`link` 是聊天记录打包（type=14），不是公众号文章或链接卡片**；链接卡片是 type=5，默认写入清单。
省略 `kinds` 时与主界面相同（图片/视频文件 + 文本和链接写入清单）；显式指定 `kinds` 时只导出这些类型的文件，不自动附带文本和链接。

## 7. MCP 兼容性与官方配置口径

| 项 | 结论 |
|---|---|
| 配置文件 | `~/.workbuddy/mcp.json`（**不带点**），顶层 `mcpServers` |

`dist/README.md` 已补齐上一轮指出的四处缺口：先安装 exe 这一步、只合并单个键不要覆盖文件、

### 关于「视频导不出」的准确口径

不是视频导不出，是**没在本机播放或转发过的视频，本地没有原文件本体**。
依据 `wechat-favorite-export/SKILL.md:34-38`：图片点开条目即下载，视频必须真的播放过；
同一批次里，点开过的图片通常都能拿到；只剩缩略图的往往是未播放过的视频。
这类在基线里是「本地仅缩略图」或「未定位本体」，不是脚本失败；
到微信播放一次再重跑导出即可升格为「完整」。进度表按状态列出文件名与原因，不笼统标「失败」。

  退到 `wxkeys.candidate_roots()` 兜底，因此微信装在非默认盘符也能找到账号目录。
- **CDN 回捞已探测，结论是不做**：`cdn_dataurl` / `cdn_thumburl` 都是一段 78–80 字节的
  不透明描述（首个类型 78 B，type=16 是 75 B，type=4 的 thumburl 119 B），里面唯一的
  可读内容是 **md5 本身**，没有 host、没有 path、没有 `encfilekey`；
  整个 `content` 里也搜不到任何 http 地址（只有 type=20 视频号自带完整 URL）。
  也就是说 URL 是微信客户端拿这段描述去走自己的 CDN 接口拼的，**不是本地能还原的**。
  因此「本机未缓存」的 45 条附件、以及 62 条语音，只能保持占位，HTML 里已写清楚原因。
